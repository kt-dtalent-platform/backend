# 마감 후 제출

## 적용 범위
공개된 IN_PROGRESS 요청은 유효 기한이 지나도 임시저장·파일 발급/완료/삭제·최종 제출·재제출을 받는다. 기존 대상자·본인 권한·버전·필수 입력·파일 완료·보완 항목 제한은 유지한다. CLOSED 요청은 최초 제출을 막되, REVISION_REQUIRED 제출은 보완 항목만 저장·파일 작업·재제출할 수 있다. 보완 기한 경과 후에도 재제출을 받고 지연 표시한다. 요청 상태와 전체 공통 기한은 바꾸지 않는다.

가장 최근 최종 제출 또는 재제출 시점이 학생의 유효 마감 이상이면 기존 submissions.is_late에 true를 저장한다. 유효 마감은 extended_due_at이 있으면 그 값, 없으면 requests.closes_at이다. 처음 제출한 submitted_at은 재제출로 덮어쓰지 않는다. 기한만 바꾸어 이미 저장된 지연 판정이 바뀌지는 않으며, 다음 재제출 시에는 그때의 유효 마감으로 다시 판정한다.

새 마이그레이션은 없다. 과거 제출의 기본값 false를 일괄 추정·보정하지 않는다.

## 프론트 연결
- 기존 담당자 제출 현황·상세 API의 late(boolean)가 저장된 is_late를 그대로 반환한다. true면 ‘마감 후 제출’ 태그를 표시한다.
- GET /v1/dashboard/manager: review.late(전체 건수), requests[].late(요청별 건수)를 추가한다. 기존과 같은 공개 IN_PROGRESS 요청·프로그램/기수 필터 범위이며 DRAFT는 세지 않는다. 보완 필요·확인 완료라도 저장된 late가 true이면 센다.
- late만 따로 조회하는 서버 필터는 추가하지 않았다. 서버 페이지 필터가 필요하면 승완의 제출 현황 API와 계약을 맞춰야 한다.

## 별도 합의·승완 연결
- 1분마다 공통 기한이 지났고 미래의 개별 연장·보완 기한도 없으며 모든 대상자의 제출이 CONFIRMED인 공개 IN_PROGRESS 요청을 CLOSED로 바꾼다. 미제출·작성 중·검토 대기·재제출·보완 필요가 남으면 기한이 지나도 열린 상태를 유지한다. 대상자가 없는 요청은 공통 기한 이후 종료한다.
- POST /v1/requests/{requestId}/close: 담당자가 미처리 인원이 남아도 수동 마감할 수 있다. 응답은 {requestId,status:"CLOSED"}. 미공개·없는 요청 404, 장학생 403, 비로그인 401. 반복 호출은 200이며 마감 감사 로그는 최초 1회만 남긴다. 프론트는 기존 제출 현황 수치로 확인창을 구성하고 확인 후 호출한다.
- CLOSED 이후에도 기존 담당자 보완 요청 API를 사용한다. 학생은 미해결 보완이 지정된 항목만 수정할 수 있으며, 내 할 일 목록에도 해당 보완 건을 노출한다. 재제출 후에는 다시 잠기며 다음 보완 요청이 있어야 수정할 수 있다.
- 기존 ReviewDecisionService의 보완 기한 지정 검증은 유지한다. 기한은 개인별 지연 여부 판정에 사용하며 전체 접수를 다시 열지 않는다. 담당자 검토 코드는 수정하지 않았다.
- 프론트·승완 인증/요청/검토 소스는 수정하지 않았다.
